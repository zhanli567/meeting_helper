# 框架、Agent Harness 与智能体范式定位

## 1. 为什么需要这份文档

智能体应用容易在早期陷入“选框架”讨论：用 Spring AI、LangGraph、MCP、公司内部平台，还是自己写循环。实际更关键的问题是：哪些边界必须由本项目掌握，哪些能力可以交给框架。

本项目的结论是：框架可以复用，但驾驭边界必须自有。

## 2. Agent Harness 在本项目中的含义

Agent Harness 不是某一个具体库，而是一组工程控制面：

- 模型适配。
- 工具注册。
- 工具权限。
- 结构化校验。
- 执行循环。
- 上下文压缩。
- 流式事件归一化。
- 人工确认。
- 观测追踪。
- 评测回归。
- 故障排查。

换句话说，Harness 是“驾驭模型的运行环境”，不是“让模型自由发挥的聊天壳”。

## 3. 业界常见范式

### 3.1 Workflow

Workflow 是确定流程。步骤由代码定义，模型只负责其中某些判断或生成。

适合：

- 发布前检查。
- 导入数据校验说明。
- 固定问答流程。

优点是稳定、可测、容易审计。缺点是灵活性较低。

### 3.2 ReAct

ReAct 是“思考、行动、观察”的循环。模型根据当前观察决定下一步调用哪个工具。

适合：

- 查询类任务。
- 少量步骤的诊断类任务。
- 用户问题表达比较自由的场景。

风险是容易循环、工具选择错误或上下文膨胀，所以必须有最大步数和重试上限。

### 3.3 Plan-and-Execute

模型先规划，再执行。执行前可让用户确认。

适合：

- 批量排座。
- 多规则排座。
- 需要解释策略的大动作。

本项目复杂排座优先采用这种模式。

### 3.4 Graph / State Machine

把智能体过程建成有状态图，例如“理解意图 -> 查询上下文 -> 生成计划 -> 人工确认 -> 执行 -> 校验 -> 总结”。

适合：

- 长任务。
- 需要暂停恢复。
- 需要人工确认。
- 需要明确失败分支。

这类模式可以参考 LangGraph，但不要求第一阶段引入。

## 4. Spring AI 的定位

Spring AI 可以帮助 Java/Spring 项目处理：

- ChatClient 调用。
- Tool Calling 抽象。
- MCP client/server 支持。
- Chat Memory。
- Advisor 链。

但本项目不应把核心业务边界直接绑定到 Spring AI，原因：

- 公司内部智能体平台已有自己的 SSE 和 tool_call 表达方式。
- 外部开发需要 DeepSeek/OpenAI-compatible provider。
- 前端草稿命令不是标准后端工具调用。
- 权限、脱敏、人工确认和审计需要贴合本项目业务。

推荐方式：

- 可以在具体 provider 或 MCP adapter 中使用 Spring AI。
- Tool Contract、Guardrails、Run State、Agent Event 不依赖 Spring AI。
- 如果 Spring AI 抽象与内部平台不匹配，以本项目契约为准。

## 5. MCP 的定位

MCP 是工具暴露协议，不是业务权限边界。

在本项目中：

- MCP adapter 可以把本项目工具注册给公司内部平台。
- MCP 工具调用进入系统后，仍然必须经过本项目工具执行器。
- MCP 工具 schema 必须由本项目 Tool Contract 生成或同步维护。
- MCP 不能绕过 meetingId 归属校验、风险等级校验和审计。

## 6. 内部智能体平台的定位

公司内部平台可以承担：

- 模型选择。
- 智能体编排。
- 技能/知识库/记忆。
- 卡片和 UI 生成。
- MCP/工具管理。

但本项目仍需保留：

- 前端统一入口。
- 后端 provider adapter。
- 本项目工具契约。
- 本项目权限策略。
- 本项目观测日志。
- 本项目草稿命令协议。

这样内部平台能力越强，本项目越容易接入；内部平台细节变化，本项目也不需要大改业务代码。

## 7. 本项目推荐组合

### 第一阶段：查询闭环

推荐：

- 轻量 ReAct。
- 自有 Harness。
- 自有 Tool Contract。
- provider adapter 支持内部/外部/mock。
- 只读工具。

不急于引入：

- LangGraph。
- 复杂记忆。
- 自动排座 planner。
- 完整 MCP server。

### 第二阶段：前端草稿操作

推荐：

- 自有 Frontend Command Protocol。
- 草稿工具独立风险等级。
- 前端执行前校验 workspaceRevision。

### 第三阶段：复杂排座

推荐：

- Plan-and-Execute。
- 人工确认计划卡片。
- 分批执行。
- 状态机或图式运行时。

此时可以评估是否引入 LangGraph 类框架，或者用 Java/Spring 自己实现轻量状态机。

## 8. 框架选择标准

只有当框架满足以下条件时才引入：

- 不要求改变本项目核心工具契约。
- 能兼容内部平台接口。
- 能保留本项目审计和 guardrail。
- 能在外部开发环境运行。
- 能明显减少重复代码。
- 失败时容易排查，不隐藏模型输入输出和工具调用。

如果框架让调试更困难，或者迫使业务代码依赖某个平台形态，应暂缓引入。
